# Reference data

The TLS evaluation judges an endpoint against a few dated lists that are compiled into the binary. Nothing is
fetched at run time. Each list records where it came from, when it was retrieved and the SHA-256 of the
downloaded source, and the About page and every endpoint's *How we tested* panel show its age. A list older
than 180 days is flagged there; it is never turned into a finding against the endpoint.

The lists live in `internal/refdata`. All of them except the lifetime table are generated by
`internal/refdata/gen` from the downloaded sources; the package documentation has the commands. The sources are
not committed.

## Licence gate

A list is bundled only after its redistribution terms are recorded here and found compatible with this
project's Apache-2.0 licence (REQ-TDAT-2). A list that fails the gate is not shipped, and the scan says the
check was not available instead of falling back to something else.

## The lists

**Root stores.** Each root's certificate is stored once and each store refers to it by SHA-256. The generator
checks every certificate parses and that the report's fingerprint matches it, and refuses a row whose status is
not *Included*. A root program's constraints are kept with the root and applied during validation:

- Mozilla's *Distrust for TLS After Date*: a leaf issued after that date is not trusted through that root. The
  date is inclusive (a leaf issued on it is still trusted).
- Chrome's `sct_not_after`: a leaf is trusted through that root only if it carries an SCT timestamped at or
  before the limit.
- Name constraints a program applies (for example Mozilla's `*.tr` on one root).

A CA that a program has removed entirely is simply absent from its store. Together, the constraints and the
absences are the distrust list of REQ-TTRS-6.

**Distrusted CA keys.** Keys no certification path should rely on: CA keys whose private half is public or
recoverable (`key-compromise`) and CA certificates root programs have blocked (`ca-distrust`). Each incident has
an id, a title, the date it became public, a summary and its sources; each entry names the CA and gives its SPKI
SHA-256 and the SHA-256 of every certificate known to carry the key. `TestDistrustListIsWellFormed` checks the
shape, and `TestEmudhraKeysAreSmallScalars` re-derives the eMudhra keys from their published private values
rather than trusting the copied hashes. Evaluation reports a listed key as `CERT.DISTRUSTED-KEY` and keeps
evaluating the chain (see methodology, eval/13). The file is edited by hand: add an incident, run
`go test ./internal/refdata/`, and set `version` to the date.

**Mozilla OneCRL.** Mozilla's list of CA certificates Firefox refuses: a few keys (subject and SPKI SHA-256) and
over a thousand CA certificates named by issuer and serial number. Only enabled records are kept. A OneCRL key
the hand-written list already has keeps the hand-written entry, which says why (a compromise, with its
incident). Every other entry becomes a `ca-distrust` entry titled "Mozilla OneCRL" with its Bugzilla link, so a
served chain through it raises `CERT.DISTRUSTED-KEY` at high severity and the store result says why the path is
not relied on. Issuer-and-serial entries can only be matched on a parsed certificate (served chains, files,
imports), not on host inventories that carry only fingerprints.

**Go's distrusted keys.** `crypto/x509` hard-codes a few SPKI hashes it refuses. The generator reads that table
from the toolchain (`-go-verify`) and fails if Go distrusts a key neither `distrust.json` nor OneCRL lists, so
the weekly refresh says so instead of letting Go hide a path without a reason.

**Age.** Each list records the day it was retrieved. The root stores, the CT log list and OneCRL count as old
after 30 days, the others after 180. An evaluation that used old root stores says so beside its trust verdict
(the report's certificate tile and chain, and `tls scan`): "Stores N days old". It is not a finding and does not
change the endpoint's score, since it is about this program's copy of the stores, not the endpoint.

**DH groups.** The primes are read from the RFC texts, checked to be prime and of the size their heading says,
and fingerprinted the way the scanner fingerprints a server's prime (SHA-256 over the big-endian bytes, leading
zeros trimmed). Fourteen of the sixteen fingerprints are pinned in a test against OpenSSL 3.5's built-in named
groups; OpenSSL has no Oakley group 1 or 2. RFC 7919 groups are reported by name as the recommended kind; an
RFC group of 1024 bits or fewer raises `KX.DH-COMMON-PRIME`. The "widely shipped defaults" from the Logjam study
are not included: no licence-clear, machine-readable list of them exists.

**CT logs.** Used only to name the log an SCT came from. T1 does not check SCT signatures.

**Lifetime limits.** Maximum validity of a publicly trusted server certificate by issue date: 398 days from
2020-09-01, 200 from 2026-03-15, 100 from 2027-03-15 and 47 from 2029-03-15. The table is pinned by
`TestLifetimeTablePinned`; change both together, from the ballot.

## Refreshing

`scripts/refresh-refdata.sh` downloads every source, runs the generator with today's date (including OneCRL and
the Go cross-check) and, given a file name, writes a summary of what changed. Then run `go test ./...` and commit
the regenerated `*_gen.go` files with the date in the message. If a source's terms change, re-run the gate above
before shipping.

The `refdata` workflow does this every Monday and proposes the result as a pull request
(`chore(refdata): weekly refresh <date>`) when anything other than the retrieval dates changed. It needs
*Allow GitHub Actions to create and approve pull requests* (Settings → Actions → General); without it the job
pushes the branch and opens an issue linking to it. CI does not start by itself on a branch the job pushed:
close and reopen the pull request to run it. If the generator fails because Go distrusts an unlisted key, the
job fails with the key's hash: add an incident to `distrust.json` by hand.
